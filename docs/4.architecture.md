# Architecture & Data Model

## 1. System Architecture

The System Architecture will be based on the Model-View-Controller (MVC), We will be using a single monolithic relational database to keep design clean and maintainable.</n> 

The **Model** layer will encapsulate the classes for each products/game, users/developers, and game categories. It will also contain the core logic behind essential features such as sorting, filtering, favoriting, and searching games The model layer will contain the connection string to the database.

The **View** layer will contain the UI/UX interface the user sees, which will be based on the Sprint 3 design models. This layer's main task is to capture user interactions and display data sent from the controller. We will aim to encapsulate a clean UI simple enough to support users like "Joe", and experienced users like "Stephan".

The **Controller** layer will act as the interface interacting between components from the View layer and the Model layer. When a user searches, filters, clicks on a game, or saves a game to their favorites, the controller handles the interaction between the Model & Controller.

The **Database** will store all application data in a single relational database, user favourites, and any new feature‑specific tables. This keeps data consistent, easy to manage, and efficient, which is ideal for both rapid development and the MVC architecture.

## 3. Data Model

### Overview

The data model uses a single relational database to store all application data. The schema is structured around the `GAMES` table as the central entity, with supporting tables for developers, platforms, genres, users, favourites, and UI categories. Many-to-many relationships are resolved through junction tables with composite primary keys.

### Entities and Relationships

#### GAMES
- The central table. Each game has a unique ID sourced from the RAWG API, a title, release date, average rating, and ratings count. A game can be linked to multiple developers, platforms, and genres through junction tables.

#### DEVELOPERS
- Stores the name of the studio or company that developed a game (`id` PK, `name`). One developer can be linked to many games; one game can have many developers. This is resolved through `GAME_DEVELOPERS`.

#### PLATFORMS
- Stores the hardware platforms a game is available on (`id` PK, `name` e.g. PC, PlayStation 5). One platform can host many games; one game can be available on many platforms. Resolved through `GAME_PLATFORMS`.

#### GENRES
- Stores genre classifications (`id` PK, `name` e.g. Action, RPG). One genre can contain many games; one game can belong to many genres. Resolved through `GAME_GENRES`.

#### USERS
- Stores registered user accounts (`id` PK, `first_name`, `last_name`, `username`, `password`, `created_at`, `pfp`, `is_admin`). Passwords are stored as hashed values. A user can favourite many games.

#### FAVOURITES
- A junction table linking `USERS` and `GAMES`. Each row holds a `user_id` (FK -> USERS) and `game_id` (FK -> GAMES) as a composite primary key. One user can have many favourites; one game can be favourited by many users.

#### CATEGORIES
- Stores UI browsing categories (`id` PK, `title`, `url`, `icon`). Linked to games through the `GAME_CATEGORIES` junction table, one category can contain many games and one game can belong to many categories.

### Relationships Summary

| Relationship | Cardinality | Junction Table |
|---|---|---|
| GAMES <-> DEVELOPERS | Many-to-Many | `GAME_DEVELOPERS` |
| GAMES <-> PLATFORMS | Many-to-Many | `GAME_PLATFORMS` |
| GAMES <-> GENRES | Many-to-Many | `GAME_GENRES` |
| USERS <-> GAMES | Many-to-Many | `FAVOURITES` |
| GAMES <-> CATEGORIES | Many-to-Many | `GAME_CATEGORIES` |

## 4. Design Decisions

<!-- Key architectural and data model decisions made by the team. -->
**Key architectural decisions**
- A key architectural decision made by the team was to develop the system with the Model-View-Controller (MVC) pattern to separate presentation and interaction from the system data this helps the code with modularity, reusability, maintainability and scalability. The system consists of 3 logical layers that interact with each other (Model, View and Controller). The Model layer will contain core features such as searching, sorting, filtering, and favouriting games this will centralise logic and improve resuability. The View layer focused on a simple and intuitive UI to cater to less experienced (Joe) and advanced users (Stephan). We chose a monolithic architecture over microservices to reduce complexity and support faster development, as a distributed system would be unnecessary for this scale.

**Key data model decisions**
- A key data model decision made by the team was to use a single relational database to ensure strong data integrity and consistency and to also show structured relationships between entities such as games, developers and platforms. We didn't use a NoSQL database as they don't have a strong relational structure required for the system and have a lack of standardization. The model uses junction tables to show many-to-many relationships this eliminates data redundancy and maintains a normalised schema. The Games table was chosen as the central entity in the database as the core features (searching, sorting, filtering, and favouriting) are built around game data this results in a logical database structure and simplified relationships between entities.

## 5. Legal, Sustainability and Ethical Considerations
**Legal Considerations**
- When designing systems like GameFinder, it is extremely important to comply with the UK data protection regulations when user information is being handled. The system should follow the principles laid out in the Data Protection Act 2018 and the General Data Protection Regulation, which require that personal data is collected and dealt with lawfully, transparently, and only for the specific purpose for which it is collected. User information, such as usernames, preferences, and activity data, should be stored only if deemed necessary for the feature specifically. To make sure the compliance is being adhered to , appropriate security measures should be implemented, including secure passwords, hashing, controlled database access, and limiting the amount of personal data being stored. The regulatory supervision is done by the ICO (Information Commissioner's Office), which executes data protection laws and could impose penalties on the organisations that fail to handle this data sincerely. 

**Ethical Considerations**
- Ethical software design choices require developers to consider the impact of the system on users. One major issue  to be addressed is privacy. Even if certain data collection is legally allowed, the system should collect only information that is important for the feature specifically, in order to lower privacy risks. One other responsibility we hold is accessibility; our services should be aimed at being usable by a wide range of users, including those with disabilities, and to ensure this, designing the system to meet standards such as the Web Content Accessibility Guidelines 2.2 helps ensure that the application remains inclusive and accessible.  It is also promoted to encourage developers to prioritise the public interest and consider the social impact of systems, which comes under promoting ethical conduct. 

**Sustainability Considerations**
- Modern software systems have an environmental impact due to the energy consumption of servers, networks, and data centres. Sustainable software design aims to minimise unnecessary workloads and optimise resource usage. Within the GameFinder, the issue of sustainability could be resolved to some extent by designing a software through efficient design practices such as optimising database queries, reducing redundant data storage, and avoiding excessive server requests. Efficient algorithms and well-structured data models reduce the load of processing needed to get results, which in turn reduces energy consumption at an infrastructure level.  These practices contribute to a more environmentally responsible software system while maintaining good performance.
